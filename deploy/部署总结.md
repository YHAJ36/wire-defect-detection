# K230 边缘端部署总结

> 2026-11-02 · 对应 WORKLOG A.9.75 ~ A.9.84
> 这份是文字稿，报告第 7 章的素材；不含过程性的试错流水账（那些在 WORKLOG 里）。

---

## 一、一句话结论

**链路通了，板端 5.0 fps，框位偏差 < 1.3 px，nano 档的量化损失只有 7%。**
但板端 mAP 没有测，PC 上的 74.67% 不能搬过来当板端成绩。

---

## 二、链路定版

```
best.pt（yolo11n，640 训，段级无泄漏）
  │
  ├─ export_nano_onnx.py      torch.onnx.export(dynamo=False, opset 12)
  │                             → yolo11n_640.onnx        10.6 MB，输出 [1,7,8400]
  ├─ make_uint8_onnx.py       把 Cast→Div(255)→Transpose 写进图头
  │                             → yolo11n_640_u8.onnx      输入 uint8 NHWC 1×640×640×3
  ├─ compile_kmodel.py        --u8raw --calib 100 --calib-method NoClip
  │                             → yolo11n_640_u8r.kmodel   3.44 MB（118 s）
  ├─ upload_kmodel.py         base64 分块 + 板上 SHA256 逐字节比对（60 s，57 KB/s）
  └─ cam_demo3.py             板上跑
```

板上单帧的六步：

```
sensor 640×480 RGB888
  → sensor.snapshot()                       采集 0 ms（阻塞在垂直同步）
  → memoryview(img) → bytearray 补边 80..560 行（填 114）   拷贝 0 ms
  → np.frombuffer(buf).reshape(1,640,640,3) → nn.from_numpy
  → kpu.run()                               推理 196 ms
  → top-8 argmax 解码 + NMS + 时域确认        解码 1 ms
  → draw_rectangle / draw_string            绘制 4 ms
  → Display.show_image(img, x=80)
```

## 三、两档实测

| 项 | yolo11s | yolo11n（定版） |
|---|---|---|
| kmodel 大小 | 11.08 MB | **3.44 MB** |
| 静态推理 | 231 ms | **172 ms** |
| 链路内推理 | 258 ms | **190~196 ms** |
| 端到端 | 2.6 fps | **5.0 fps** |
| 上传耗时 | 190 s | 60 s |
| 分数损失（板端/PC） | 0.55（中位，6 图） | **0.927（中位，8 图）** |
| 连跑内存 | — | 770 帧稳定 2573 KB |

帧率构成（n 档）：采集 0 + 拷贝 0 + 推理 196 + 解码 1 + 绘制 4 = **5.0 fps**。

n 只比 s 快 1.34 倍，而 FLOPs 少 3.4 倍——说明 KPU 在薄层上利用率低，
**缩小模型不能线性换帧率**。再要快只剩降推理分辨率一条路（640→480 约掉 5~8 pt），没做。

## 四、正确性核对

同一张 `board_case/testcase.bin`，分别喂 PC 的 ONNX 和板上的 kmodel：

| 项 | PC | 板上 | 偏差 |
|---|---|---|---|
| top1 类别 | 1 (thunderbolt) | 1 | 一致 |
| 框中心 cx / cy | 341.6 / 257.6 | 342.3 / 257.3 | **0.7 / 0.3 px** |
| 框宽高 w / h | 28.8 / 28.5 | 27.5 / 27.5 | 1.3 / 1.0 px |
| top1 分数 | 0.597 | 0.361（s 版） | 见下 |

量化台阶是 2.5 px（640 输入下单个量化单位的边长），框位偏差在台阶的一半以内，
**管线正确，不需要再怀疑预处理**。

分数那一栏是 s 版的老数据，n 版已重测，见第五节。

## 五、本次更正的三条（都是之前的结论有错）

### 1. 「分数压到 0.6 倍」是错的

A.9.78 用 `firc_xianlan_1175` **一张图**比了一次（0.5972 → 0.3613 = 0.605×），
就写成了通用系数。实际上：

- 同一批数据里 6 张 s 版的比值是 0.497 / 0.826 / 0.605 / 0.917 / 0.449 / 0.447，
  **中位 0.55，跨度 0.45~0.92**——不是常数。
- 那 6 张全是 **s 版**，最终部署的是 **n 版**，两版量化配置不同。

用 `deploy/calib_scores.py` 重测 n 版（8 图 / 640 anchor / 有效 77 点）：

| 区间 | 板端 / PC | \|Δ\| 中位 |
|---|---|---|
| 全区间 | **0.927** | 0.033 |
| PC > 0.5 | 0.969 | — |
| PC > 0.7 | 0.979 | — |

### 2. 「屏幕上置信度只有五十」不是量化造成的

n 版上 0.50 对应 PC 约 0.54，差 4 个点。真实原因是模型对桌面、显示器边框、头发
这类**分布外目标**本来就只给五十分。归因从「量化压缩」改回「分布外」。

### 3. 换 nano 是意外赚的

原以为小模型要付精度代价，实测量化损失反而从 s 的 ~45% 降到 n 的 ~7%。
FLOPs 少 3.4 倍、模型小 3.2 倍、帧率快 1.9 倍、分数标度还更准，四个方向都占。

## 六、六个坑（都是会卡住半天的那种）

| # | 坑 | 现象 | 正确做法 |
|---|---|---|---|
| 1 | 串口被占 | `failed to access COM8` | `canmv-backend.exe` 独占，`taskkill //F //PID` 它；**不用关 VSCode** |
| 2 | mpremote 传文件慢 | 4.5 KB/s | 别用 `repr(bytes)`（膨胀 4 倍），改 base64 → 57 KB/s；波特率无用（USB CDC） |
| 3 | `nn.from_numpy` 是拷贝 | 循环外建 tensor，top1 只变 1 次 | 每帧重建 tensor |
| 4 | 输出张量泄漏 | 每帧漏 235 KB，跑久了 OOM | `del out` + 每 5 帧 `gc.collect()` |
| 5 | ai2d 不可用 | `builder.run()` 硬件异常、USB 失联 | 这版固件的 ai2d 四种配置全崩；改 `np.frombuffer(img)` 直读帧内存 |
| 6 | 类别顺序 | 屏幕上的类名整体错位 | 以 `data.yaml` 为准：`['break','thunderbolt','wear']` |

第 5 条要特别说：ai2d 崩溃会让板子 USB 失联，**只能拔插**。全程没写 flash、
没碰 `K230BurningTool`，SD 卡上只有 kmodel 和日志。

## 七、能报什么、不能报什么

**可以报：**

- 端到端 5.0 fps（640×480 采集 / 640×640 推理）
- 框位偏差 < 1.3 px（量化台阶 2.5 px 的一半内）
- 分数标度损失 7%（n 版）
- 连续 770 帧内存稳定 2573 KB
- n 档精度不劣于 s（640 配对 +0.90 pt，CI [−2.74, 4.13] 跨零）

**不能报：**

- PC 上的 74.67% / 0.7907 **不能当板端成绩**。中间隔着一层量化，真实 mAP 需要在板上
  跑满 203 张 test 才能定，**没测**。
- 不能说「板端误检是缺陷」。那是训练分布外，端侧修不了。
- 不能说「nano 比 s 精度高」。CI 跨零，是打平。
- 不能说「5 fps 够用」。没在实际巡检场景下测过持续运行和发热。

## 八、如果要自己手动走一遍（不依赖这套脚本）

**需要准备的东西：**

1. **nncase 2.11.0** —— 嘉楠的编译器，pip 装 `nncase` + `nncase-kpu`。
   依赖 .NET 8 运行时，Windows 上必须设 `DOTNET_ROLL_FORWARD=LatestMajor`，否则 import 就报错。
2. **CanMV 固件** —— 板子出厂/烧录的版本要带 `nncase_runtime`。
   在 REPL 里 `import nncase_runtime` 能过就说明有。
3. **一份校准集** —— 100~200 张**真实场景**图，不要用训练集的子集充数。
   校准集决定量化的动态范围，用错会让分数整体偏掉。
4. **ONNX** —— `opset 11 或 12`。opset 13+ 有些算子 nncase 2.11 不认。

**流程四步：**

```
pt → onnx（torch.onnx.export, dynamo=False）
   → kmodel（nncase.Compiler: import_onnx → use_ptq → compile → gencode_tobytes）
   → 传上板（mpremote / SD 卡 / base64 分块，大文件建议直接拷卡）
   → 板上跑（nn.kpu() → load_kmodel → set_input_tensor → run → get_output_tensor）
```

**搜的时候认这几件事，能少踩一半坑：**

- 讲 nncase 时**带版本号**的才可信。2.4 / 2.7 / 2.9 / 2.11 的 API 不一样，
  混着抄会报看不懂的错。
- 讲 `ai2d` 的教程，先确认它的固件版本和你一致。这版固件的 ai2d 是坏的。
- 输入预处理（mean/std/归一化）**要么在编译时用 `preprocess=True` 声明，要么写进 ONNX**。
  两边都做会做两遍，都不做会少做一遍——这两种错都不会报错，只会让分数莫名其妙偏低。
- 校准方法（Kld / NoClip / MinMax）对分数分布影响很大。Kld 会把分数封顶，
  本项目实测封在 0.544，换 NoClip 才放开。

**官方资料位置：** 嘉楠 nncase 的 GitHub 仓库（有 API 文档和示例）、
K230 CanMV 的在线文档站（固件 API 和例程）、立创庐山派的教程页（板级接线和烧录）。
